## Phase 2 — Supabase database + storage

### 2.1 Create Supabase project

1. Sign in at [supabase.com](https://supabase.com) with owner account.
2. Create new project in region **ap-southeast-1 (Singapore)** or **ap-south-1**.
3. Record: **Project URL**, **DB connection string** (Transaction mode, port 5432),
   **service-role key** (never browser/APK).

### 2.2 Enable PostGIS

In Supabase SQL editor:
```sql
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS postgis_topology;
SELECT PostGIS_Version();  -- must return a version string
```

### 2.3 Verify migration role can CREATE EXTENSION

The connection string used for MIGRATION_DATABASE_URL must use the **postgres** superuser role
(Supabase connection string with role `postgres` and `?sslmode=require`). The runtime
`DATABASE_URL` uses a least-privilege `anon` or custom app role after migration.

### 2.4 Create private storage bucket

1. In Supabase → Storage → New bucket: `sahitol-media`, **Private** (not public).
2. Policy: API server's service-role key has read/write; no public access.
3. Record bucket name as `sahitol-media` (matches `SUPABASE_STORAGE_BUCKET`).

### 2.5 Take pre-migration backup

For a fresh Supabase project there is nothing to back up — skip to 2.6.
For subsequent migrations: `pg_dump "$MIGRATION_DATABASE_URL" > backups/pre_migration_$(date +%Y%m%d).dump`

### 2.6 Run Alembic migration

```bash
export MIGRATION_DATABASE_URL="postgresql+psycopg://postgres:<password>@db.<project>.supabase.co:5432/postgres?sslmode=require"
cd services/api
alembic upgrade head              # must complete without error
alembic current                   # must show HEAD
```

### 2.7 Verify schema and row counts

```bash
python -c "
from app.db.session import SessionLocal
from sqlalchemy import text
with SessionLocal() as db:
    result = db.execute(text(\"SELECT table_name FROM information_schema.tables WHERE table_schema='public' ORDER BY table_name\")).fetchall()
    print(f'{len(result)} tables present')
"
```

Expected: ≥41 tables (matching `docs/06_SCHEMA.md`).

### 2.8 Run production seed

```bash
export DATABASE_URL="$MIGRATION_DATABASE_URL"   # or app-role URL after grant
cd ../..                                         # repo root
python scripts/seed_production.py               # must report 0 errors, commit OK
```

Verify seed counts:
```bash
python -c "
from app.db.session import SessionLocal
from sqlalchemy import text
with SessionLocal() as db:
    for tbl in ['materials','material_aliases','safety_guides','facilities','price_observations']:
        n = db.execute(text(f'SELECT COUNT(*) FROM {tbl}')).scalar()
        print(f'{tbl}: {n}')
"
```

## Phase 3 — Render API deployment

### 3.1 Connect repository

1. Sign in at [render.com](https://render.com) with owner account.
2. New → Blueprint → connect the SahiTol GitHub repository.
3. Select `render.yaml` at repo root.

### 3.2 Set secret environment variables

In Render Dashboard → Environment for `sahitol-api`, set these (not in render.yaml):
- `DATABASE_URL` — Supabase app-role connection string with `?sslmode=require`
- `MIGRATION_DATABASE_URL` — Supabase postgres-role connection string (for alembic)
- `SUPABASE_URL` — `https://<project>.supabase.co`
- `SUPABASE_SERVICE_ROLE_KEY` — from Supabase dashboard (API settings)

The following are auto-generated by Render from `render.yaml`:
- `JWT_SECRET_KEY` (generateValue: true)
- `PIN_PEPPER` (generateValue: true)

### 3.3 Update CORS and URL env vars after first deploy

After the Render service first deploys, note its URL (e.g. `https://sahitol-api.onrender.com`) and update:
- `PUBLIC_API_BASE_URL` = `https://sahitol-api.onrender.com`
- `CORS_ORIGINS` = `https://sahitol.pages.dev,https://sahitol-api.onrender.com`

### 3.4 Verify health endpoints

```bash
curl https://sahitol-api.onrender.com/health/live   # must return {"status":"live",...}
curl https://sahitol-api.onrender.com/health/ready  # must return {"status":"ready","database":"connected","storage":"connected","storage_probe":"adapter_readiness",...}
curl https://sahitol-api.onrender.com/              # must return app name, version, problem
```

### 3.5 Render free-plan cold start

Render free services spin down after 15 minutes idle. First request after idle takes ~30–60s.
This is documented; no keepalive automation is pre-authorized.

```

https://sahitol.pages.dev/admin/overview    # must load app, not 404

  .then(r => r.json()).then(console.log)
// Must return status "ready" with database/storage "connected", not a CORS error
```

## Phase 5 — Android release APK

### 5.1 Update production API URL

In `apps/android/app/src/main/res/values/strings.xml` (or `BuildConfig`):
```
api_base_url = https://sahitol-api.onrender.com
```

Release `network_security_config.xml` already permits HTTPS only. Verify no cleartext origins.

### 5.2 Generate signing keystore (owner only)

```bash
keytool -genkeypair -v \
  -keystore sahitol-release.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias sahitol-release \
  -storepass <owner-password> -keypass <owner-password>
```

**Store outside this repository.** Back up the `.jks` file and passwords separately.
Record keystore SHA-256: `keytool -list -v -keystore sahitol-release.jks | grep SHA256`

### 5.3 Build release APK

```bash
cd apps/android
./gradlew assembleRelease \
  -Pandroid.injected.signing.store.file=<path>/sahitol-release.jks \
  -Pandroid.injected.signing.store.password=<store-pass> \
  -Pandroid.injected.signing.key.alias=sahitol-release \
  -Pandroid.injected.signing.key.password=<key-pass>
```

Record APK path: `app/build/outputs/apk/release/app-release.apk`
Record APK SHA-256: `certutil -hashfile app-release.apk SHA256` (Windows) or `sha256sum` (Linux).

### 5.4 Install and verify on real phone

```bash
adb install app/build/outputs/apk/release/app-release.apk
```

Verify:
- Clean install, demo login works, no debug secrets
- Upgrade from debug build preserving Room/outbox data
- Offline airplane-mode launch after one successful sync

## Phase 6 — Hosted cellular acceptance test

Using a **phone on cellular** (not laptop LAN):

1. Cold-start app → login/demo mode
2. Fetch facility directory (online)
3. Upload photo → create lot → sync → check API received
4. Two-phone QR confirmation flow
5. Payment acknowledgement
6. Admin export download
7. Redeploy API (trigger from Render dashboard) → wait for restart → retrieve same private photo
8. Test unavailable backend: put phone in airplane mode → verify graceful retry, no duplicate op

Record:
- Deployed API URL and version
- Render project ID (no secrets)
- Supabase project ID (no secrets)
- Pages URL
- APK version, versionCode, SHA-256
- Health check results
- Cold start duration
- Any failures and their resolutions

## Rollback

- **Web:** Redeploy previous Cloudflare Pages deployment (UI or `wrangler pages deployment list`).
- **API:** Redeploy previous Render deployment via dashboard.
- **Database:** Only roll back if schema is compatible with previous code. If migration was destructive, restore from backup: `pg_restore --clean -d "$MIGRATION_DATABASE_URL" backups/<snapshot>.dump`

**Do not blindly downgrade API code after real writes to a migrated schema.**
